什么是skill

定义：

  • 逻辑定义上，是“有记忆的、可复用的领域专长”，这与tool的“无记忆的、一次性的函数调用”对应
  • 物理结构上，是一个文件夹，包含指令文档、参考资料、可执行脚本等资源

例：

比如一个 pdf-editor 技能文件夹里，可能有一份"怎么处理 PDF"的操作指令、一个旋转 PDF 的 Python 脚本、一份 API 参考文档——AI 不需要从外部再找任何东西，这个文件夹里全有了。

标准结构

anthrotic的渐进式披露skill结构设计

  • 第一层为skill.md中前置YAML中的name和description，第一层需要让agent知道何时应该使用，这部分会并入prompt
  • 第二层为skill.md的主体，包含技能的详细信息，采用第三人称进行编写
  • 第三次层为捆绑额外的文件，用于解决单个skill上下文信息包含过多的问题。可通过文件名和引用这些文件，如reference.md、script.md等

skill.md的设计规范

  1. 根本约束-简洁： 上下文窗口是有限的，每一句话都要值得它占用的token，无效信息越多，对其他能力的影响就越多

  2. 三级加载： 元数据->body->捆绑资源。

    • L1元数据用于判断是否需要激活技能
    • L2body为技能的主体，触发后才加载
    • L3捆绑资源（工具箱）包括：
      • scripts：脚本，用于被agent执行而不是被读取，agent只需要发出运行指令，而不需要解析脚本内部代码
      • references：只读的参考文档，如API接口文档、技术规范、业务规则、常见问题解答
      • asserts：客观可验证的评分标准

skill-creator落地

## 书写约束-简洁 一个前提假设：AI本身已经足够聪明，只需要补充他不知道的东西 - 用简洁的示例代替冗长的解释，好的示例要胜过大段的文字描述

四类捆绑资源的区别

Scripts

确定、可靠或需要确定性重写的任务

References 文档和参考材料，在需要时加载到上下文，辅助思考过程，例如API文档，领域知识，公司政策，详细工作流指南

Assets 不会加载到上下文，直接用于产出物的资源，如图片，字体，ppt模板，html样板

渐进式披露的三种方式

高层指南+参考文件

使用类似目录的形式将skill提供给ai

按领域组织

先按照目的导向判断需要哪个方面的skill，如处理文本，图片相关等，然后在领域中查找

条件性细节

直接展示基础功能，高级功能按需展示

常见错误

错误 后果 修正
触发条件放在 body 里 body 是触发后才加载的，晚了 放 frontmatter description
"When to Use This Skill" 写在 body 同上，Codex 已经决定用了才看到 移到 description
参考细节塞进 SKILL.md body 膨胀，信息密度下降 拆到 references/，body 只放引用链接
确定性操作写成文字指令 AI 每次重新理解，可能出错 封装成 scripts/，执行不读入
references 互相引用 AI 需要多跳获取信息 所有 references 从 SKILL.md 直接链接
SKILL.md 和 references 内容重复 浪费 token，更新时可能不一致 信息只在一处存在

AI自由度限制

ai擅长理解语义，生成文本，做创造性工作，不适合精准格式控制、长度约束、命名规范

  • 高自由度（文字指令）：多种方法都可行时，决策依赖上下文，用启发式引导。
  • 中自由度（伪代码/带参数的脚本）：有最佳实践但允许变通，配置影响行为。
  • 低自由度（具体脚本，少量参数）：操作脆弱容易出错，一致性至关重要，必须遵循特定序列。

接入方式

  • 基于文件和代码的声明式接入：在特定目录下存放skill.md
  • 运行时动态发现和按需加载：渐进式披露，agent内置根据运行需求加载相关skill的能力
  • 基于标准协议与网关的集成：MCP协议标准化
  • 写约束时，不能怎么做要比怎么做好，前者是将信息域压缩到一定范围内，后者是给出一定的方向引导
  • 统一使用祈使语气，祈使句天然就是指令
