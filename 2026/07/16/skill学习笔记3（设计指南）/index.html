一、skill核心定义

告诉agent，在什么条件下，按照哪些步骤，产出什么结果。

（一）常见误区：

1.skill与Prompt的区别

Prompt更偏向于临时性、探索性和即兴交互，没有长期复用性，不需要明确的输入输出，注重一次性的解决问题，skill则是一个可长期复用的、输入输出明确的能力模块，强调稳定、确定和易于工程化维护

2.skill的面向对象

skill的阅读者是模型而不是人，因此不需要讲解为什么、原理是什么，skill的核心是下达指令而不是使之明白原理，模型不需要知道为什么这么做，只需要知道怎么做和做什么

3.skill的复杂程度与产生作用的关系

Skill并不是越复杂越强大，模型处理能力有限，过余的skill文档不止会占用相当一部分上下文，还会导致skill的启用、使用条件变得模糊，导致错误启用等问题。 同时，能力复杂的skill边界模糊，也会降低命中率和稳定性

二、Skill设计原则与标准

（一）精确的元数据

  • name简洁、唯一、规范，避免语义模糊
  • description采用第三人称、含有关键词，避免冗余。从模型视角描述。明确核心功能和触发时机的关键词让模型快速匹配用户需求，使用当...时加载skill进行... 而不是该skill用于帮助进行...

（二）根据任务场景合理约束模型

合理的约束能减少模型使用skill时的不确定性，但过强的约束会限制模型的灵活性，以下为三个约束强度分级：

1.高自由度：给原则，让模型灵活决策

适用于存在多种有效方法，模型的决策依赖上下文进行灵活决定，如代码审查、技术方案分析等没有固定执行步骤的场景

这类场景适合采用启发式策略，给出原则引导模型做出合理决策

2.中自由度：给框架，让模型在规范内变通

适用于存在首选模式、允许一定程度的变通、行为受配置参数影响的场景，如报告生成、数据统计等

这类场景需要给出一定的框架结构，让模型在遵循大框架的前提下，对细节进行自主策略择优

3.低自由度 ：给固定步骤，模型严格执行

适用于操作脆弱且易错、流程一致性重要的场景，如数据库迁移、系统部署等。该类任务需严格按照固定步骤执行，每个步骤的错误都可能导致严重成果

这类场景需要给出明确的执行步骤，明确各个阶段的细节，每个具体操作需要具体详细说明

（三）skill的核心标准

1.边界明确

skill的易发问题是不知道什么时候该做而不是不知道怎么做。触发条件需要有明确的正向条件和负向条件，包括什么情况使用和什么情况不能用

2.输入输出结构化

定义人机沟通的语言，避免出现模糊描述，保证可解析性

3.步骤明确可执行

skill的核心便是怎么做，执行描述需要具体、指令式而不是概括性、描述性的：

比如对于“PR测试Skill”，只写“检查PR，运行测试，然后更新状态”，这样的描述过于笼统，模型无法明确“检查PR”具体要检查什么、“运行测试”要按什么顺序执行、“更新状态”要更新到什么平台，很容易出现执行偏差。

而规范的指令式步骤，应该明确每一步的具体操作，让模型能直接照着执行，示例如下：

Steps:

Validate PR: 检查prId和branch是否有效，若无效则返回错误信息，终止执行。

Checkout branch: 切换到指定的branch分支，确保获取到最新的代码。

Run tests: 根据runTests参数执行单元测试，若runTests为true，执行全部单元测试；若为false，跳过测试步骤。

Collect results: 收集测试结果，整理成testReport格式，若测试失败，记录具体的错误日志。

Update PR status: 将测试状态（成功/失败）回写到PR页面，方便开发者查看。

Notify user: 若测试失败，通过系统消息向用户返回错误信息和日志链接；若测试成功，无需额外通知。

4.失败策略完备

遇到skill执行失败情况，模型往往会自由发挥做出不可预期的行为，因此需要有对常见失败场景的明确处理方式

5.职责绝对单一

每个Skill只做一件事，对应一个核心动作名词，避免把多个不想管的功能捆绑在一个skill中

三、如何构建可迭代的skill

Skill开发是一个以失败为起点、评测为牵引、持续迭代优化的工程化过程，而不是先写再测试。skill不是基于假设的规则结合，而是针对已暴露问题的最小化解决方案。以下为构建skill的六个步骤：

（一）构建无skill基线，识别真实问题（确实是没考虑过这个）

不使用skill的情况下，直接让模型执行目标任务，作为和后续对比的基准。该步骤主要识别模型在执行目标任务时的真实问题和能力缺口，为后续的Skill开发和评测提供依据。

很多开发者跳过这一步直接写，导致Skill解决的是自己假设的问题，而不是实际存在的问题，以下为这一步的三个重点观察方面：

  • 模型在哪些情况下表现不稳定或结果不可复现
  • 哪些输入会引发模型的歧义、误解或走偏
  • 模型是否在错误的时机主动帮助 这些失败点和不确定性为本质上就是Skill需要解决的真是能力缺口，也是和后续评测的核心

（二）以失败优先为原则，定义评测用例

优先编写评测用例而不是直接开发skill。评测是约束，skill是落地实现，脱离评测约束直接开发会放大大模型的不确定性。评测用例需注重以下三个关键信息：

  • 什么场景下属于Skill的正确使用范围
  • 什么场景下Skill拒绝执行或判定为失败
  • 什么样的输出结果才算稳定可用

（三）编写最小化Skill，明确最短成功路径

依旧先跑起来再说，能跑起来再优化

（四）补充边界条件与结构化示例

承接上一步，逐步完善功能，扩展适用范围。主要包括以下三部分：

  • 补充更多边界场景以及更多对应的行为约束
  • 明确Skill输入、输出的结构化定义
  • 补充关键的输入、输出示例

（五）评测回归与持续迭代

结合新的问题持续迭代优化，让迭代始终与评测结果强绑定：

  • 新增评测用例，明确新的需求和约束，确保能通过新的评测用例同时不会破坏原有功能
  • 修改Skill：每次修改都要重新运行所有已有评测用例然后进行回归验证
  • 评测、进一步优化：若评测未通过，优先简化Skill而不是盲目叠加新规则

(六)结合真实使用路径进行校准

四、让Skill可维护、可扩展、降低长期管理成本

（一）渐进式披露

之前的笔记有过记录，不做记载

（二）工作流与反馈闭环

对于包含多个步骤，且中间结果会影响最终质量的复杂任务，需要建立有效的反馈机制，防止执行过程中出现步骤遗漏、执行顺序混乱、中间步骤的错误无法及时修正。

（三）可执行脚本的加固

Skill本身不会理解或阅读脚本的代码逻辑，只能感知输入和输出，因此一旦脚本产生了预期之外的输出，模型就只能猜测，因此脚本必须遵循失败可预期、输出可理解、参数可解释的原则

五、依托Ai快速创建和迭代Skill

  1. 通过让Ai对自己执行真实任务的结果进行结构化复盘，创建简单的Skill初稿，然后基于复盘得到的初稿，加之人工快速评审入库。
  2. 后续使用中，根据新暴露的问题，让ai依照反馈进行更改并验证
