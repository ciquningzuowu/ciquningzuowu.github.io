Claude Code 学习笔记：框架设计

摘要

  • 上下文摘要的触发可以有agent自己判断，相关细节需要进一步看更多技术文档了解
  • 最小化创建：优先编辑现有文件而不是创建新文件
  • 创建专门的压缩策略skill
  • 之前一直疑惑的一个问题：Skill的内容如果会被压缩就会损失，那么要如何将其注入给agent合适，答案是，维护专门的skill类型，不会被压缩
  • claude的user-remainder是与user-input合并输入的，会被压缩，但是可以在触发压缩后的新的一次对话后再次注入
  • 一些没思考过的工具作用：
    • 用户交互：向用户提问，触发选择框
    • 进入plan模式
  • 多级结构解决问题：通过中层节点对底层节点的总结遏制底层节点传入太多信息的问题
  • LLM 智能体在实时协调和委派其他智能体方面还不够出色

思考

  • 了解一下OWASP十大漏洞
  • 并行、串行工具的逻辑判别与设计

一、System message

结构：

  • 角色定位
  • 安全与合规边界
    • 仅支持经过授权的、安全的代码，拒绝破坏性的技术实现要求
  • 保证URL的真实性
    • 禁止生成或猜测URL，仅能使用用户提供或本地文件的URL
  • 系统机制
    • 输出格式：非工具调用的文本会被直接展示给用户，你可以用 GitHub Markdown格式。
    • 权限与重试：工具调用需要用户批准，如果用户拒绝，你不要重复相同的调用，而是调整策略或询问原因
    • 系统标签：工具调用结果和消息可能包含<system-reminder> 等标签，这些标签和实际内容无关。
    • 提示注入：若结果含可以注入，立即向用户标记
    • hook机制：用户可配置hook响应事件，其反馈视为用户输入；若被阻止需调整或检查配置。
    • 历史压缩：达到上下文长度限制时，你会自动压缩旧消息，这样你和用户的对话是没有上下文限制的。
  • 如何做事
    • 上下文理解：将模糊指令置于当前代码库和任务重解读，直接修改代码而非仅给建议
    • 尊重用户判断：不要质疑任务规模
    • 先读后改：修改前必须阅读并理解目标文件
    • 最小化创建：优先编辑现有文件，而不是创建新的文件
    • 不预估时间：聚焦于需要完成的任务·，而不是工作需要多长时间完成
    • 受阻时换方法：不暴力重试，寻求替代方案或询问用户
    • 安全编码：避免 OWASP 十大漏洞，发现不安全代码立即修复
    • 拒绝过度设计：仅做请求的更改，不添加无关功能、注释、错误处理等
  • 谨慎执行操作。低风险操作随便做，高风险操作需要用户同意：
    • 破坏性操作（删除、覆盖、rm、-rf）
    • 难以逆转的操作（强制推送、重置、修改依赖）
    • 影响他人/共享状态的操作（推送代码、评论PR、发送消息）
    • 若用户明确要求更高自主权，可跳过确认，但仍需要注意风险
  • 如何使用工具
    • 专业工具优先：能用read、edit、glob等，就不要使用命令行
    • 不要滥用subagent
    • 技能调用：用Skill执行用户自定义的skill命令，不要猜测
    • 并行、串行调用：无依赖的工具可以并行来提高效率，有依赖的按顺序调用
  • 沟通风格
    • 只有用户要求时采用emoji，否则避免
    • 回复简短，直击要点
    • 提及函数、代码时附带文件路径:行号，方便用户跳转
    • 工具调用前：用句号结束上线爱文，而不是冒号
  • Auto Memory系统
    • 文件持久存储
    • 定期更新、删除错误记忆
    • 保存的内容包括：稳定的模式、架构决策、重要路径、问题解决方案（看着像skill开发，不确定是不是作者弄混了）
    • 不保存的内容：会话临时信息、未核实的猜测
  • 当前环境快照
    • （当前目录的结构）

二、claude.md

claude1会在项目目录里放一个claude.md，每次启动时claude都会自动读取。里面描述了一些关于项目的重要信息，以及一些需要模型时刻遵守的约束。claude.md有多个层级，例如全局用户级别、项目级别、模块级别。

claude.md不是会被拼接到system promopt的，而是会在某些user信息中以<system-reminder>形式存在。这种处理方式的一大特点就是因为不改变system prompt导致缓存友好

三、工具

1.部分有记录意义的工具

（1）用户交互

主动使用工具触发用户交互

（2）计划模式

官方定义了 7 类应该用的场景：

  1. 新功能实现 —— 哪怕很小，从 0 到 1 都有隐含决策
  2. 多种合理方案 —— 比如"加缓存"可以是 Redis / 内存 / 文件，选择本身就是设计
  3. 修改现有行为 —— 动之前先说清楚改什么
  4. 架构决策 —— 选模式、选依赖、选数据流方向
  5. 跨 3 个以上文件的改动 —— 影响面大到 diff 看不出全貌
  6. 需求本身不清晰 —— 需要先探索、先讨论方向
  7. 用户偏好会影响实现 —— 如果 Claude 想用 AskUserQuestion 来澄清，那更应该用 EnterPlanMode

以及 4 类不该用的场景：

  • 单行修复（修 typo、off-by-one）
  • 只添加一个函数，需求非常清晰
  • 用户已经给出非常具体详细的指令（用户自己已经在规划了）
  • 纯研究/探索任务（应该用 Agent tool，不涉及后续实现）

2.设计思想：高/中/低层工具的合理搭配

一个需要思考的问题：提供高层抽象工具，让 Agent 像调用函数一样完成复杂任务；还是提供低层原子工具，让 Agent 自由组合。

平衡高级抽象工具和基础工具选择的关键在于模型擅长的是什么

命令行工具可以使用curl和wget命令获取和下载网页内容，但是网也内容还需要处理可能的网络错误，以及处理内容、解析HTML。将这些操作封装成高层抽象工具，就能实现稳定的全流程处理，使得模型可以专注于核心任务（分析网页内容等）而不是纠结于中间环节的细节。

设计tool的时候，关键在于观察模型在实际任务中的表现，发现它的舒适区和薄弱点，然后针对性的设计工具，把模型不擅长的步骤封装成工具。

四、Sub-Agent

好处：

  • subagent的作用：节省Agent上下文，前面已经提到了
  • 并行探索，效率更高
  • 广度优先的问题上处理效果显著优于单agent 坏处：
  • 烧钱：多agent本质上实在有限时间投入更多token解决问题

1.适合使用subagent的任务情景

  • 高度并行化的任务，能够拆解出大量互不依赖的子任务
  • 信息量远超单个上下文窗口承载能力

2.不适合使用subagent的任务场景

  • 需要共享上下文。老生常谈，并发容易导致一堆冲突，且变动还会产生关联影响，agent之间传递信息也要处理
  • agent之间存在大量相互依赖关系的任务。目前LLM之间的协调能力还不够成熟，容易出错或延迟
  • 变成任务大多不适合，代码的逻辑往往是线性的，需要紧密的模块间协作，很难拆分成大量独立的子任务（让我想起之前的合作项目开发，如果通信协议没做好，真的一言难尽）

3.subagent设计

按重要功能大方向分化，以下为claude方案：

  • 一个全能代理+一个探索和理解代码代理+一个plan规划师+状态栏配置subagent+claude产品指南

4.多agent协调模式

（1）Orchestrator-Worker

一主多辅，简单可控

存在的问题：

  • 单点瓶颈：所有中心化系统的通病，所有流量都要经过中心节点
  • 中心节点需要相协调居合所有子任务的结果，如果子任务较多，会差生很大的上下文压力
  • 无法紧密协作：工作节点之间需要通信必须强制经过中心节点，延迟高

（2）Hierarchical

树结构，逐层下分任务。因为中层向上层汇报时会将细节总结成摘要，所以有效解决了主节点上下文压力。

存在的问题： LLM在实时协调和委派正难题方面不够出色，且创建子智能体太多，易产生无限递归和滥用子Agent（ 不过个人感觉多级结构解决主节点上下文压力这个设计很不错）

查阅了一些关于 “LLM 智能体在实时协调和委派其他智能体方面还不够出色” 相关的信息，大致有下：

  1. Orchestrator（指挥官）本身会随着任务变长、日志增多先于子agent崩溃
  2. 当前的训练模式本质都是单人自主式训练，而不是协作环境
  3. 沟通本身亦是一项成本，且在多层agent结构里是不小的一项成本
  4. 最简单的一集：大多数任务单智能体都能很好的完成

（3）Mesh

agrnt之间建立显式的点对点链接，直接传递信息

存在的问题

  • 缺乏全局视图：如果没有中央节点持有完整状态，各个Agent需要靠自己拼凑因果链
  • 状态一致性问题：访问共享资源时的问题

工业界中Mesh一般会增加一个中央协调节点在Mesh之上

五、Agent Team

类似Orchestrator，分一个领导与多个成员，但是成员之间可以相互通信。

成员之间共享任务列表但是不共享上下文，通过自主领取或领导指派获取任务完成权，通过文件锁防止其他成员重复获取任务。

成员之间可以通信，同时又有一个中央协调节点，这是前面所述的Mesh与Orchestrator的聚合方法
