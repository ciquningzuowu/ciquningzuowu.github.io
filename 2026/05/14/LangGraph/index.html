两个基础体系

1.使用Graph API

定义模型节点与工具节点以及边函数，创建图对象，将前述对象全部注入后，调用.compile()方法将静态图转化为实际执行对象。全局通过state进行状态传递

2.使用函数式API

函数式api中无需显示定义节点和边只需要在单个函数汇总编写标准控制流逻辑接口

使用@task装饰器创建节点，使用@enterpoint创建代理（内部逻辑为接收模型返回的内容，然后进行模型回复中要进行的工具调用，并将工具结果与历史信息一并再次发送给模型，循环直至返回的xmessage里不再有工具调用请求，将所有的内容返回

LangGraph中的思考

用langgraph构建智能体时，首先将其划分为不同的节点，然后描述每个节点的决策和状态转还好你，最后，通过一个共享的可被所以节点读写的state连接不同的节点

以下为大致的构建流程：

1.绘制工作流图

区分每个步骤，每一步都是一个节点，并简述这些步骤相互之间连接方式

2.确定每一步需要做什么

确定每个节点进行的操作类型以及需要的上下文：

  • LLM步骤：需要进行理解，分析，生成或进行推理决定
  • Data步骤：需要从外部源获取信息
  • Acction步骤：需要执行外部操作
  • User input步骤：需要用户接入

3.设计state

state是用于追溯记忆的关键，需要存入state的信息可通过以下两个问题判断：

  • 是否该信息需要跨步骤存在
  • 能否从其他信息推导出它，能则不需要存储

state保存的信息应尽量原始，而不是格式化后的文本：

  • 不同节点可以对同一个原始数据进行更适合该节点的格式化
  • 可以通过原始信息进行更好的调试

4.构建节点

LangGraph中的一个节点实际就是一个获取当前state并返回更新后的state的python函数

工作流和代理

设置工作或代理需要模型支持结构化输出和工具调用的聊天模型。

工作流的实现

langgraph的工作流有图形api和函数api两种实现。

  1. 图形api实现主要是通过创建图、创建节点、创建关系、实例化图
  2. 函数api实现主要与正常语句在语法上没有太大差别，主要是通过装饰器@task和装饰器@entrypoint进行异步并行自动编排和断点续传（当工作流因为崩溃、人工审核等中断后再次启动时，会依据保存在checkpointer中的状态在断掉的地方继续执行）。被修饰的函数会成为类似新进程的不会阻塞主进程的对象，需要调用.result方法才能获取执行结果

工作流的并行化（多节点向单节点输入）

  1. 图形化api的工作流并行化主要是通过多个节点与同一个节点创建edge实现
  2. 函数式api的工作流并行是通过在@entrypoint中不调用.resullt方法阻塞等待实现的

路由（单节点向多节点输入）

  1. 图形化api的路由实现并不复杂，只是通过add_conditional_edges方法擦混关键一对多关系，传入始节点、路由决策器函数（通过state进行判断，返回代表下一步方向的字符串）、路由节点的字典（将路由函数的返回内容映射到具体的节点）
  1. 函数式api的路由功能实现也是通过编写一个路由决策函数，并在调用@task函数前使用决策函数进行判断，然后通过python的基础逻辑分支控制进行实现

动态创建节点

依旧使用add_conditional_edges设置下一节点，通过决策器决策需要创建多少新的工作节点，使用send功能创建多个执行任务，langgraph会将任务转为具体节点，并在最后通过增量更新机制将多个节点的结果汇总

评估器-优化器

使用优化器审查评估其的输出结果，如果评估器或人工认为响应需要改进，则提交反馈并重新生成相应，重复循环直至生成可接受的响应。这是用于任务有特定成功标准、需要迭代才能满足标准的情况

工具节点

langgraph有预构建的工具节点ToolNode，能够自动处理并行工具执行、错误处理和状态注入

能力

持久化

langgraph内置了持久层没见过图状态保存为检查点，执行的每一步会保存图状态的快照，并将其组织成线程，这可以有效支持人机协作、对话式记忆、时间旅行调试和容错执行。

  • 人机协同需要再经过人工处理后能以中断时状态恢复执行
  • 记忆
  • 时间旅行：重放之前的图执行过程以查看和调试特定的图步骤
  • 容错：若果场任务在一个或多个节点发生故障，可以从最后一个成功步骤重新开始执行

核心概念

  1. 线程：checkpointer保存不同线程的state时需要一个线程id来区分state是属于哪一个线程，这通常需要通过在调用时设置一个包含线程id的config字典来实现
  2. checkpointer：线程中某超级步骤的state的快照，由StateSnapshot对象表示
  3. super-steps：
    • 核心在于“全局同步”与“版本更新”。每次检测阶段会检测所有满足运行条件的节点进行活化变为actie态，本次的所有运行节点即为一个超级步，langgraph会约束同一超级步内的所有节点的进程结束再结束本个超级步，然后重复检索所有已经满足运行条件的节点。
    • 如果某些节点的前置条件部分满足，则会处于等待状态（因此如果前置条件节点因为一些原因直接结束，如直接运行到end，则会导致该节点陷入死锁，所以需要确保一定会后传信息）。
    • 同一超级步内每个节点运行完时都会将结果写入checkpointer_writes表，这有助于当该超级步骤内的其他节点发生错误时已完成节点的结果不会丢失，再恢复时无需重新运行。
    • 超级步骤还会持久化节点的写入操作，这可以实现在故障时的容错，通过检索不完善的StateSnapshot，时间旅行即可只重新进行之未成功的任务
  4. 检查点命名空间：每个checkpointer都有一个命名空间字段，用于表示它属于哪个图或子图。
    • 当命名空间为""(空)时，说明它是属于最上层父图的checkpointer
    • 当期不为空时，格式为"node_name:uuid",说明它是属于给定节点的子图，uuid则是用来唯一标识的（例如第几次调用等）使用|可以表示嵌套子图。
    • 通过RunableConfig的["configurable"]["checkpoint_ns"]可以从节点内部访问命名空间
  5. 获取和更新状态：与已保存的图的state交互，需要通过线程标识符，通过graph.get_state(config)可以获取最新的节点的图state，这会与通过config中提供的线程id对应的最新的StateSnapshot对象（或者当提供了checkpointer的id时会直接返回与其关联的checkpointer）

StateSnapshot字段：

field type description
values dict checkpointer的state通道值
next tuple 下一个要执行的node，若为空则意味着已结束
config dict 包括thread_id,checkpoint_ns，checkpoint_id
metadata dict 执行的元数据，包括source（触发原因，包括input输入触发，loop循环触发，update人工干预更新触发），writes（节点输出表），step（超级步计数器）
created_at str 检查点的iso 8601时间戳
parent_config dict|config 前一个检查点的配置
tasks tumple 步骤要执行的任务的id，使用时为子图快照name

通过提供进程id和调用graph.get_state_history(config)可以获取图的完整的执行上下文历史，这会返回一个与提供的thread id对应的StateSnapshot列表对象（时间倒序排列）

更新状态

通过update_state方法可编辑state，这会创建一个包含更新值的新的checkpointer 而不会修改原来的对象，这种修改方式是受归约函数约束的。

通过制定as_node参数，可以让此次更新伪装为由某个节点发出的，这会影响下一步的行为

memory store（长期记忆）

  • state schema指定了在图的运行过程中会被填充的键值对，这在图的运行过程中可以传递信息，但是当需要跨thread传递信息时，则需要依靠store
  • 记忆通过元组划分命名空间，命名空间的长度和含义可以使任意的。
  • 使用store.put可以向命名空间存入记忆，需要提供命名空间（类似文件夹路径）、记忆的唯一标识（uuid）、记忆的内容三个参数
  • 使用store.search可以读取命名空间中的内容，该方法会返回指定命名空间下的内容列表
  • 命名空间下的每个记忆类型都是一个类，可以使用.dict方法进行访问，其字段包括value，key，namespace，created_at，updated_at
  • 使用list_namespace可以查找存在的命名空间，类似os.list，可通过前缀、后缀、目录深度三种方式查询
  • store支持语义搜索，使用需要配置一个嵌入模型，指定需要嵌入的字段，然后即可在调用search时通过query参数实现语义查询
  • 在使用put存储记忆时可指定那些字段进行向量嵌入（向量嵌入是单个实体进行，而不是针对实体类型进行）
  • langgraph-checkpoint-postgres为使用postgre数据库的checkpointer，包括PostgreSaver和AsyncPostgreSaver
  • 检查点接口：put（存储一次state），put_writes（记录不完整的临时改动），get_tumple（获取某次会话某刻的state），list（查看存储的state列表）
  • 序列化器：state中经常包含各种python对象（字典、列表、自定义dataclass、第三方库数据类型等），调用put存储是数据库并不能直接理解这些对象，序列化器可以将这些复杂的python数据打包成数据库能存储的统一格式（bytes），相应的，在使用get_tuple和list方法时也会自动解包这些bytes类型数据，将其还原为存储时的类型。默认的打包器为JsonPlllusSeriallizer。对于特殊的无法解析的特殊类型，可使用Python自带的pickle协议进行兜底打包，组织需要将打包器的pickle_fallback参数设置为True
  • 可以使用EncryptedSerializer.from_pycryptodome_aes序列化加密器对state进行静态加密（防止因数据库泄露导致数据泄露），使用方法为准备一个AES密匙环境变量LANGGRAPH_AES_KEY，序列化加密器会自动从环境变量读取该变量（或者手传key参数），然后将加密序列化器传递给checkpointer的serde参数，即可使所有使用.put传入的数据都会被自动加密
  • 序列化加密器的高级使用：可以通过LANGGRAPH_AES_JSON_KEYS环境变量配置对哪些json字段名进行加密

持久执行（Durable Excution）

本模块的持久执行不止意味记忆数据存储，还意味着进程中断后的无缝重新接续（这尤其体现在human-in-the-loop情景和长任务的interruption、error），通过保存已完成的任务，持久化执行使得一个进程可以直接从先前未进行的步骤重新开始（即使经过相当长的时间间隔后）

langgraph内置的持久层为工作流提供持久执行，确保执行的每一步都被都会被持久化保存

Requirments

  • 在工作流中指定会保存工作流进程的checkpointer
  • 运行工作流式指定线程标识

确定性和一致性重放（Determinism and consistent reply）

  • langgraph的接续并不是视频播放那样，在断点的代码部分继续进行，而是重放当前节点。所以需要将所有不确定性操作或应该避免次重复执行的操作封装在单独的task里以确保当工作流恢复执行时不会重复执行这些操作
  • 不确定操作举例：如果节点中有从数据库获取某个值，重新执行只会获取当前的正确值，但如果是获取一个随机数，第一遍时在断点之前给了一个随机数，第二遍又会给另一个随机数，对于用户，则是决断后原数据丢失，或者调用llm，llm的回答也具有随机性，随机操作如果重放会导致不同的结果
  • 避免重复执行操作举例：像是追加写入、删除等操作，如果出重复执行，会导致重复内容或操作对象已经无法进行操作等
  • 总结：保证当工作流失败进行重试时，效果与首次执行时相同

Durability modes（持久模式）

Langgraph支持三种持久模式，可根据应用程序平衡性能和数据一致性。下为三种模式：

  • exit：仅在图执行成功退出或认为中断时保存更改，这种模式对长时间运行的图能提供最佳性能，坏处是中间状态不会保存，无法从过程中的崩溃中回复
  • async：执行下一步操作时异步进行持久化更改，这提供了良好的性能和持久性，但存在执行过程中崩溃则会无法写入刚刚完成的那一步检查点的风险（因为程序崩溃可能导致另一个异步写入上个节点状态的进程也崩溃）
  • sync：langgraph在执行下一步之前同步持久化更改，代价是一定的开销

节点中使用任务（using task in nodes）

如果一个节点包含多个操作，将每个操作转换为一个task比将操作重构为单独的节点更好，这可以保证前述的确定性与一致性，task对象的执行情况是会保存的

恢复工作流程（Resumeing workflows）

  • 可以使用interrupt函数暂停中断工作流然后发送Command对象来恢复执行
  • 发生异常后会自动从上次成功的checkpointer恢复工作流（需要提供线程标识符和None，None会让智能体意识到没有新输入，任务是继续之前的执行）

优雅暂停(drain)

可以在调用invoke和stream时传入RunControl控制器实例，这可以控制在超级步后暂停并保存好当前状态，只需要在任意一个线程中调用request_drain方法。这个操作会等待当前超级步结束再停止。使用inoke（None，config（带有thread_id））可恢复执行

访问drain状态

通过runtime可以访问，这可以用于当节点中有比较耗时的任务，并且检查到当前超级步后会停止，则会运行简化流程，快速出结果

drain使用示例

在实际的服务器运维中（如 Docker、K8s），系统要关闭一个服务时，通常会先发送一个 SIGTERM 信号。可以将signal和control绑定（一旦信号被发送，绑定的就控制器对象就会收到信号），并处理引发的GraphDrained异常

容错性（fault tolerance）

当节点发生故障，langgraph提供了三种可组合的响应机制：

  • 重试：根据异常类型和返回设置
  • 超时：限制单次请求持续时间
  • 错误处理：尝试次数用尽后运行恢复函数 可以通过set_node_defaults对所有节点一次性配置这些机制，而无需在每次add_node调用时重复配置

重试策略

add_node时设置retry_policy参数，传入重试器，可添加的参数包括以下：

  • max_attemps：最大尝试次数
  • initial_interval：第一次重试前的时间
  • backoff_factor：每次重试时的乘数
  • max_interval：两次重试之间的最大时间间隔
  • jitter：添加随机抖动
  • retry_on：发生哪些错误时重试

自定义重试逻辑（custom_retry_logic）

传递一个可调用对象处理各种异常类型，并使用default_retry_on进行默认执行

检查重试状态

通过访问runtimexecution_infonode_attempt可以访问以下字段（即使没有设置重试策略也可访问execution，这种情况重试次数默认为）：

  • node_attempt：当前尝试次数
  • node_first_attempt_time：首次尝试的时间戳
  • thread_id：当前执行线程的id
  • run_id：当前执行的运行id
  • checkpoint_id：当前的检查点id
  • task_id：当前执行的任务id

超时策略

add_node时设置timeout参数，可填入秒数、timedelta对象（datetime库中的对象，为时间长度）、TimeoutPolicy对象（可以设置节点实际执行的最长运行时间和等待下一步的最长空闲时间）。需要注意的是，超时策略仅可以为异步节点设置，同步节点如果被设置，运行时会报错

进度信号（progress signals）

默认情况下refresh_on为auto，节点运行监控时钟会在以下情况重置：

  • state被写入
  • 流式输出模式时向外输出了字段
  • 子任务被调度
  • 运行时调用了runtime stream_writer
  • 所有回调事件，如llm输出token、工具调用、chain的开始和结束

以上策略可以使用.set_node_defaults设置模板

补充

  • 父图的设置不会被子图继承
  • API式node设置这些策略的方式为@task的参数
  • 超时策略仅适用于一步操作
  • error_handler本身如果发生错误会向上冒泡

  • Fork：修改一个已存储的checkpoint创建新分支来探索可选路径

Replay

所谓的重放恢复执行，实际只是根据提供的的checkpoint_congfig，从指定checkpoint开始执行

Fork

从checkpoint创建一个新的分支，新分支的state会通过checkpoint链（parent、next）进行区分管理，使用方法为调用update_state创建更新一个state，然后invoke时使用该checkpoint的config并传入None为input就继续执行

as_node

调用update_state使用as_node可以传递本次更新是由那个节点发起的，这在以下三种情境中比较有效：

  • 并行分支（Parallel Branches）：因为超级步的缘故，无法确认最后一次更新是由谁发起的
  • 无执行历史（No Execution History）：新线程上无执行历史
  • 跳过节点：设置as_node为一个未执行的节点，会直接从后续节点进行运行，未执行的节点会被直接跳过（例如某个节点是用来产生注入中间值到state的，如果已经知道了确定的值，可以直接注入跳过该流程）

  • long_memory：store

Short_memory

  2. 提供SQLSaver
  • checkpointer会自动从父图传播到子图

子图（subgraphs）

概述：将一个完整的图作为另一个图的节点使用，以下为该架构较为有用的情景：

  • 创建多智能体协作系统
  • 多个图中重用节点
  • 分布式开发

两种使用方式：

  1. 将子图作为节点： 使用情景：父图和子图需要的state schema不同，需要包装函数将父状态映射到子图以及将子图输出映射回父状态
  2. 在子图中调用另一个图： 使用情景：父子图共享状态keys，不需要包装函数

子图实现

  • 将子图作为节点的实现方式仅仅是简单的在一个图的节点中调用另一个图（invoke、stream）

子图持久性

子图的持久性需要特别注意，可以通过调用.compile（）时设置checkpointer的参数为：

  • Per-invocation（None）（default）： 每次调用时刷新并继承父图的checkpointer来支持单词调用中的interrupt和可持续化执行
  • Per-thread（True）：同一线程中的调用会累积state，每次新调用会接续上次调用进行
  • Stateless（False）：完全没有checkpointer，运行方式和普通函数相同，没有中断和持久化执行

状态化（stateful）

状态化子图继承父图的checkpointer，这使得支持中断和持久化执行以及state审查。

三种模式

  • Per-invocation（default）：当每次对子图的调用都是独立的时（子代理不需要知道自己之前的运行消息），设置checkpointer为false或none。（仍然可以通过父图的checkpointer实现中断和持久化）

  • Per-thread：当子代理需要记住之前的每次交互时，可以使用该模式

  • Stateless：当需要子代理以类似普通函数的形式被调用的时候使用此模式

子图流式输出

要包含子图输出到流式输出中时，可以在父图的stream方法设置subgraphs选项为true ,这会同时流式输出父图和所有子图的输出

部分执行

对于由大型图组成的代理，可能希望测试代理内部的部分执行路径，而不是端到端的整个流程。在某些情况下，将这些部分重构为子图可能更符合语义，可以像往常一样单独调用这些子图。如果不想更改代理图的整体结构，可以使用 LangGraph 的持久化机制来模拟代理在所需部分开始之前暂停，并在所需部分结束时再次暂停的状态。步骤如下：

  1. 使用检查点编译您的代理（内存中的检查点InMemorySaver足以进行测试）。
  2. 调用代理的update_state方法，并将参数设置为要开始测试的节点_之前的_as_node节点的名称。
  3. thread_id使用与更新状态时相同的命令调用代理，并将interrupt_after参数设置为要停止的节点的名称。

向后兼容性（Backward compatibility）

软件程序是不断变更升级的，变更升级时不可能将所有任务都结束然后用新程序覆盖，只能将其暂停，然后与新程序做兼容。以下为变更新程序时现需要注意的事：

技术兼容性：新代码必须能够加载并针对现有状态执行，旧版中断程序的完成是依靠state进行的，但是这里的state是中断时的程序（老版本的代码）存入的，如果新代码有逻辑改动，便会产生冲突：

  1. 恢复执行是依靠state中存储的next字段进行恢复，但是如果新程序的node名字发生改动甚至node被删除，则会出现之前中断的程序无法找到下一步有安排进行的节点
  2. state中的键在新程序中更换了键名，而下游或旧的检查点依然使用原名对该键进行访问
  3. state中新增了字段或更改了字段约束，例如新增不能为空的必填字段，但访问字段的程序并不在开头，而是在程序中间，导致前半段会因为state中的字段不能为空出错

一些推荐操作：

  • 新增字段使用Optional[.....]
  • 先添加新字段再删除旧字段，在弃用期对两者进行双写和路由，直到通过运行日志确认正在运行的线程已经不再依赖与旧的字段或节点后，将其删除
  • 保持节点对未知键的容错性，TypeDict运行时会忽略额外的键，因此除非节点中会显式读取缺失的键，否则不会触发旧版本代码的state异常
  • 使用time driver在新程序正式部署之前对流程进行抽查
  • 如果一个节点或键不会再被使用，那么运行完成的流程后，rutime和checkpointer中不会有相关的记录，可以通过这个确认是否已经可以摘除

业务兼容性

有时程序更新没有错误，但是新图和旧图的运行逻辑不同，不希望让旧的中断状态在新的图逻辑运行，可以通过增加一个版本字段，根据state中储存的版本在node中增加处理逻辑，使得旧的state可以以旧的逻辑重新运行完

非确定性（Non-determinism）

这条规则主要是为了处理interrupt和task，任务恢复执行时，会按顺序填入interrupt的值和task的运行状态（之前的超级步完成缓存记录），即如果在新程序中这两者发生了删减和顺序变换，就会使得对于interrupt值和task是否运行过状态的混乱

Graph API与Function API的选择

概括：当您需要对工作流结构、复杂分支、并行处理或团队协作优势进行明确控制时，请选择Graph API 。如果您希望以最小的更改将 LangGraph 功能添加到现有代码中、拥有简单的线性工作流程或需要快速原型功能，请选择函数式 API 。

Graph API的优势情景：

  • 调试和文档的复杂工作流可视化
  • 跨多个节点共享数据的显式状态管理
  • 具有多个决策点的条件分支
  • 需要合并的并行执行路径
  • 团队协作中，视觉呈现有助于理解

Function API的优势情景：

  • 对代码修改较少，不会出现大幅重构的情况
  • 使用规范的控制流（if\else、循环、函数调用）
  • 函数的状态无需显式状态管理
  • 快速原型开发，减少样板代码
  • 线性工作流+简单分支逻辑

Graph API的使用

常用的State Schema方式：

  • TypeDict：轻量级，简单高效
  • dataclass：支持默认值定义
  • Pydantic：递归数据验证

Command

  • update：进行state 更新
  • goto：导航到特定特定节点
  • graph：从子图跳转父图（在该参数填入Command.PARENT）
  • resume：提供值进行interrupt恢复

一些使用规则：

  1. 节点中存在Command时，需要给节点函数指定目标节点的类型注解

作用：

  • 图渲染：生成可视化图时正确显示所有可能的路由
  • 静态验证：LangGraph编译时验证节点可达性
  • 类型安全：防止运行时路由到不存在的节点

  1. Command的goto产生的是动态边，不会影响静态边界（使用add_edge添加）的触发，因此尽量避免混用，否则会导致同时触发两条运行分支

  2. 不可在invoke和stream时使用update参数，调用时传入Command不会导致从头开始而是从最新的checkpoint恢复执行，推荐使用updte_state和invoke时直接传入参数，然后按照归约器规则进行更新

  3. 可以让tool节点返回Command以同时实现状态更新和动态路由，注意要避免混用，工具驱动的动态路由和静态边只使用一个

递归限制（Recursion limit）

限制一次调用执行的超级步上限，通过config的recursion_limit参数设置

运行步数相关

可以通过使用config参数（RunableConfig）获取各项配置参数，包括langgraph_step，也可以通过在state中添加一个RemainingSteps对象统计距离最大超级步数限制还有多少步

两种处理逻辑：内部监控步数提前干预，外部捕获异常

defer

在add_node时使用，用于解决一个超级步约束无法处理的问题，设置了defer的节点在图中有其他节点正在执行任务时不会执行，用于处理前置分支不止一条且长度不同的情况

Runtime

Pregel管理实现了LangGraph的运行应用，使用setGraph或@enterpoint时会产生一个可以被输入invoke的Pregel实例。

概括：Pregel包括actors（node）和channels（state），actors从channels读写数据，

Actors

每个Actor都是一个PregelNone，从chnnel中读写数据，PregelNodes实现了LangChain的Runnable接口

Channels

用于连接actors，每个channel都有value type、update type、update function

  • LastValue:默认通道类型，会存储最后写入的值，覆盖先前的值，用于将数据跨步骤传递
  • Topic：可配置的发布、订阅通道，用于发送多个值或累计跨步骤的输出，可设置为去重或累计期间写入所有制
  • BinaryOperatorAggregate：存储一个持久值，通过对当前值和每次update应用二元运算符更新（累加、累计）
  • DeltaChannel(byte)：仅存储每个步骤的增量而不是完整的所有累计值

Bulk Reducer

DeltaChannel的reducer，接收当前state和所有来自当前step的writes队列
